## 阶段 0：仓库与上游源码基线

- 参考源码必须先固定版本，再运行和分析；跟随 `main` 会让截图、结论和调用链不断漂移。
- 上游依赖和自有依赖要隔离：上游源码位于忽略目录，Docker 服务使用独立项目名和端口。
- Docker Desktop 的 registry mirror 可能瞬时返回 502，应先重试，再考虑更改全局镜像配置。
- Node 版本应与上游开发容器对齐；本仓库使用隔离的 Node 20，不把系统 Node 24 当成默认运行环境。
- Corepack 可能把缓存写到用户 AppData，并在 Windows 上出现 `EXDEV`；直接运行 Corepack 下载的 `yarn.js`，同时把 `YARN_CACHE_FOLDER` 和 `YARN_ENABLE_GLOBAL_CACHE=false` 指向 D 盘，可以绕开包装层问题。
- Next.js telemetry 会写用户 AppData；若该目录出现跨卷重命名错误，设置 `NEXT_TELEMETRY_DISABLED=1` 后重新启动。
- Windows 的 TCP 排除区间会阻止 Docker 绑定某些端口；选择宿主端口前先检查 `netsh interface ipv4 show excludedportrange protocol=tcp`。

## 阶段 1.2：基础设施与请求 ID

### Spring 配置

- `application.yml` 负责公共配置，`application-local.yml` 和 `application-api.yml` 只在对应 profile 激活时覆盖。
- `${DB_URL:默认值}` 表示“环境变量优先，默认值兜底”，避免把连接信息写进 Java 代码。
- Hikari 的 `connection-timeout` 是等待连接池归还连接的时限，不是 SQL 执行超时。
- Flyway 的资源前缀必须是 `classpath:`；`class:` 会被判定为未知前缀并导致启动失败。
- MyBatis-Plus 的 `map-underscore-to-camel-case` 只负责结果集字段映射，不是数据库字段改名。

### 请求 ID 生命周期

```text
HTTP 请求
-> RequestIdFilter 读取或生成 ID
-> RequestIdContext 供 Java 代码访问
-> MDC 供日志框架访问
-> X-Request-Id 响应头供客户端关联
-> finally 清理 ThreadLocal 和 MDC
```

- `RequestIdContext` 使用 `ThreadLocal`，它服务于当前处理线程，不是用户级或全局存储。
- Filter 使用 `OncePerRequestFilter`，避免同一请求在转发等场景下重复执行。
- `@Order(Ordered.HIGHEST_PRECEDENCE)` 让请求 ID 尽早建立，便于后续 Filter 和业务日志使用。
- 客户端 ID 只允许长度受限的安全字符；非法输入使用 UUID 替代，降低日志注入风险。

### 统一成功响应

- `ApiResponse<T>` 固定包含 `data`、`message`、`requestId`，避免每个 Controller 自定义成功响应结构。
- 工厂方法集中处理默认消息和请求编号，私有构造器阻止调用方绕过统一组装规则。
- `requestId` 在响应对象创建时从 `RequestIdContext` 取得快照；后续修改线程上下文不会改变已经创建的响应对象。
- 泛型让调用方在编译期知道 `data` 的真实类型，避免 `Object` 和强制类型转换造成的隐式错误。

### 统一错误响应

- 成功和失败使用不同协议：成功使用 `ApiResponse<T>`，失败使用 `ErrorResponse`，避免把错误码和字段 details 塞进成功模型。
- `ErrorCode` 使用枚举把错误码、HTTP 状态和默认消息绑定在一起，业务代码不能随意传入裸数字状态码。
- `ErrorResponse` 使用私有构造器和工厂方法统一组装响应，`requestId` 只能来自 `RequestIdContext`。
- 错误 details 为空时规范化为 `{}`，非空时通过 `Map.copyOf` 保存不可变快照，避免外部后续修改污染响应对象。
- `BusinessException` 负责携带业务错误码、安全消息和 details，不直接依赖 Controller 或 HTTP 响应对象。
- `@RestControllerAdvice` 中的 `@ExceptionHandler(BusinessException.class)` 负责把异常转换为 `ResponseEntity<ErrorResponse>`，HTTP 状态来自 `ErrorCode`。
- MockMvc standalone 测试同时挂载请求 ID Filter 和异常处理器，可以验证真实状态码、响应 JSON、响应头和 requestId 贯通。

### 健康检查

- `live` 表示进程是否还能响应请求，不应调用 MySQL、Redis 或其他可能一起故障的外部依赖。
- `ready` 表示应用是否具备处理核心业务的条件，必须检查关键依赖；不可用时返回 HTTP 503，而不是用 200 加业务字段表示失败。
- MySQL 使用 `Connection.isValid(timeoutSeconds)` 验证连接池中拿到的连接仍然有效，检查完必须通过 try-with-resources 归还连接。
- Redis 使用 `PING/PONG` 验证连接和认证都正确；只验证 TCP 端口可连接不能覆盖密码错误。
- 任一依赖失败时仍继续检查另一个依赖，可以一次返回完整的 `mysql`、`redis` 状态。
- 健康检查返回的 details 只包含安全的 `UP/DOWN` 状态，不返回 JDBC URL、异常消息、密码或主机信息。

### MyBatis-Plus 配置

- `com.baomidou` 是 MyBatis-Plus 的官方 Maven 组织 ID，不是随机的第三方重新打包。
- 分页能力依赖 `mybatis-plus-jsqlparser`，由 `PaginationInnerInterceptor(DbType.MYSQL)` 解析 SQL 并生成分页语句。
- Mapper 扫描应在真实 Mapper 出现后配置，避免空扫描范围和启动期噪声。

### Flyway 迁移

- Flyway 默认版本文件名格式是 `V<version>__<description>.sql`，版本号和描述之间必须有两个下划线。
- Flyway 已经连接到应用配置的数据源，迁移脚本只应改变该数据库的 schema，不应负责 `CREATE DATABASE` 或 `USE`。
- 已成功执行的迁移文件不能修改；Flyway 会校验校验和，结构变化要新增更高版本文件。
- `flyway_schema_history` 是迁移审计表，至少检查 `version`、`description`、`checksum` 和 `success`。
- 唯一索引允许多个 `NULL`，所以可选邮箱可以用 `NULL` 表示未填写；业务层仍需把空字符串规范化为 `NULL`。
- `DATETIME` 不携带时区信息，第一版约定由 Java 业务代码写入 UTC 语义的时间，不能依赖容器本地时区作为事实来源。

## 阶段 1.4：鉴权基础设施与注册输入

### 会话 Token 与 JWT 的区别

- Sa-Token 默认签发的是不透明 Token，本身不承载用户信息；服务端在 `SaTokenDao` 中保存 Token 到登录 ID 的映射，“你是谁”靠查会话得到。
- JWT 把声明放进 Token 自身并用签名防篡改，验证不查存储；代价是退出、改密、封禁无法只靠 Token 本身立即生效，仍然要引入黑名单或版本号。
- 本项目选择 Redis 持久化的 Sa-Token 会话：换取明确的注销语义和多实例共享能力，代价是每次鉴权访问 Redis。
- `is-share: false` 让同一账号的多次登录各自持有独立 Token，注销其中一个不会误伤其他会话。
- `token-prefix: Bearer` 和 `is-read-header: true` 一起把取值来源限制为 `Authorization: Bearer <token>`，避免同一套 Token 从 Cookie 或请求体被隐式读取。
- Bean 只暴露 `PasswordEncoder` 接口而不是 `BCryptPasswordEncoder` 实现类，业务层就只依赖“能哈希、能校验”的契约，将来更换算法不影响调用方。

### 异常到 HTTP 契约的适配

```text
受保护接口调用 StpUtil.checkLogin()
-> Sa-Token 判定未登录，抛 NotLoginException
-> @RestControllerAdvice 拦截该异常
-> 映射为 ErrorCode.AUTH_REQUIRED
-> ErrorResponse 从 RequestIdContext 取快照
-> ResponseEntity 决定 HTTP 401
-> Jackson 序列化为 JSON 响应体
```

- “是否登录”的判定由 Sa-Token 完成，异常处理器不做认证判断；它是把内部异常翻译成稳定外部协议的适配层。
- 响应体不是处理器直接“发送”的：处理器返回 `ResponseEntity<ErrorResponse>`，真正的写出由 Spring MVC 参数解析与 `HttpMessageConverter` 完成。
- 统一使用固定的“请先登录”，不把 Sa-Token 的 `NOT_TOKEN`、`TOKEN_TIMEOUT` 等内部原因回显给客户端，减少攻击者试探空间，也避免客户端耦合框架细节。
- 出现两种 401 错误码是有意的：`UNAUTHORIZED` 是通用语义，`AUTH_REQUIRED` 专门表示“这次请求需要先登录”，便于前端统一触发跳转登录。
- 兜底 `@ExceptionHandler(Exception.class)` 记录带 requestId 的完整堆栈到日志，但只向客户端返回 `INTERNAL_ERROR`，把“排查信息”和“对外信息”分开。

### Testcontainers 与 Sa-Token Redis 集成

- `@DynamicPropertySource` 在 Spring 容器启动前把容器的随机端口写入配置，因此应用连的是本次启动的真实 MySQL/Redis，而不是本机固定端口。
- 测试断言 `SaManager.getSaTokenDao()` 是 `SaTokenDaoForRedisTemplate`，证明自动装配确实换成了 Redis 实现，而不是默默退回内存 DAO；只断言“键值能存”无法证明这一点。
- `dao.getTimeout()` 断言的是区间而非精确值，因为写入到读取之间的时间流逝不可控。
- Testcontainers 版本要与 Docker Engine 的 API 版本匹配；`docker` CLI 正常不代表 Java 客户端也能正常连接，两者是独立的协商路径。

### MyBatis-Plus 实体映射（阶段 1.4B）

- 驼峰转下划线是机械规则：在每个大写字母前插入 `_` 再转小写。所以 `passwordHash -> password_hash`、`createdAt -> created_at` 都正确，但 `createAt -> create_at` 就会映射到不存在的列，插入时报 `Unknown column 'create_at' in 'field list'`。框架不认识英语，字段名拼错不会被纠正。
- 主键策略必须和 DDL 对齐：列为 `AUTO_INCREMENT` 时要写 `@TableId(type = IdType.AUTO)`。MyBatis-Plus 默认的 `ASSIGN_ID` 会先生成雪花 ID 再插入，自增列等于被绕过。
- `BaseMapper<T>` 不需要实现类，MyBatis 在启动时用动态代理生成并注入；但接口必须被 `@MapperScan` 或 `@Mapper` 扫描到，否则容器里没有可注入的 Bean。`@MapperScan("com.webcollector.**.mapper")` 让新增模块的 mapper 自动被纳入，不必每加一个模块改一次配置。
- `insert` 之后断言主键非空，是验证 `IdType.AUTO` 生效的最直接方式；主键由数据库生成并回写到 Java 对象，而不是由框架提前生成。
- `selectById` 后逐字段断言，是验证“Java 字段 ↔ 数据库列”映射是否正确的唯一可靠手段。代码能编译只说明类型正确，不说明映射正确。
- `DATETIME(3)` 只精确到毫秒，Java 的 `LocalDateTime` 精确到纳秒；测试里用 `truncatedTo(ChronoUnit.MILLIS)` 对齐精度，否则断言会因为被数据库截断的纳秒而失败。
- 测试唯一约束时要隔离变量：验证“用户名唯一”时把两个用户的邮箱设成不同值，否则无法判断是哪个唯一键触发了冲突。
- 数据库唯一索引是并发场景下的最终防线，业务层的“先查询再插入”只是为了让错误信息更友好；两者不是替代关系。

### 输入规范化与校验（阶段 1.4B2）

- `String.trim()` 只删除编码小于等于 `U+0020` 的字符，删不掉全角空格 `U+3000`；`String.strip()` 基于 `Character.isWhitespace`，能删掉它。中文输入场景优先用 `strip()`，否则用户粘贴的全角空格会一路进入业务层。
- 规范化和校验有严格的先后顺序。Bean Validation 在对象构造完成之后才运行，因此把规范化放进 record 的紧凑构造器，`@Size` 校验的就是规范化后的值；如果把规范化推迟到 Service，`"  ab  "` 会因为“长度 6”通过 `@Size(min = 3)`，而 Service 拿到的是 strip 后只剩 `"ab"` 的非法值。校验和业务层看到的必须是同一个字符串。
- record 的紧凑构造器只能给**参数**赋值（`username = ...`），编译器会自动把参数写回字段；写 `this.username = ...` 会编译失败。这个限制是 record 语法的一部分。
- 小写化要传 `Locale.ROOT`，不要用无参 `toLowerCase()`。无参版本依赖系统默认语言环境，在土耳其语环境下 `"I".toLowerCase()` 得到 `"ı"`，同一个邮箱在不同机器上会被规范化成不同字符串。
- `@Email`、`@Size`、`@Pattern` 都把 `null` 视为有效值，只有 `@NotNull` / `@NotBlank` 拒绝 `null`。“邮箱可选”因此不需要任何额外判断，空字符串在规范化阶段转成 `null` 之后就自动通过。
- 密码不做任何规范化。用户密码里的首尾空格可能是刻意设置的，strip 掉之后用户用原样密码就登不进去了；拒绝纯空白密码交给 `@NotBlank`，两件事互不冲突。
- 校验规则的上限要和 DDL 对齐（`VARCHAR(254)` 对应 `@Size(max = 254)`）。对不上时，要么放过数据库装不下的值（插入报 500），要么把数据库装得下的值挡在门外。
- 纯函数（如规范化工具类）应该有独立的单元测试，不依赖 Spring 容器和数据库；这样的测试毫秒级完成，能在没有 Docker 的环境里反复跑，是回归防护里性价比最高的一层。

### 注册接口闭环（阶段 1.3；旧 1.4.3）

- 注册是一个应用服务用例：`AuthController` 只做 HTTP 边界和 `201 Created`，`AuthService` 负责注册开关、重复检查、BCrypt、时间和事务。
- “先查询用户名/邮箱是否存在”只能提供友好错误，不能替代数据库唯一索引；并发请求仍由唯一键做最终裁决，`DuplicateKeyException` 必须翻译为安全的 `409`。
- 注册时间通过注入的 `Clock` 生成，并截断到毫秒，与数据库 `DATETIME(3)` 精度对齐；测试使用固定时钟可以精确断言 `createdAt` 和 `updatedAt`。
- `Instant` 在 standalone MockMvc 的默认 Jackson 配置下可能被序列化成数字时间戳；给 `UserSummary.createdAt` 加 `@JsonFormat(shape = JsonFormat.Shape.STRING)` 后，对外契约稳定为 ISO 8601 字符串。
- 注册测试分为三层：`AuthServiceTest` 验证业务分支，`AuthControllerTest` 验证 HTTP 契约，`AuthRegistrationIntegrationTest` 验证真实 MySQL、Redis、BCrypt 和 Mapper 的完整链路。
- 测试方法前使用单行 `// [测试意图] ...` 说明验证的行为和边界；测试名说明“做什么”，测试意图注释说明“为什么要验证它”。
- 阶段 `1.3`（旧 `1.4.3`）完成时全量测试从 55 项增加到 70 项；新增 6 个 Service 测试、6 个 Controller 测试和 3 个真实数据库集成测试。

### 登录与会话生命周期（阶段 1.4、1.5）

- `AuthService` 不直接调用 `StpUtil`，而是依赖 `SessionTokenService`。这样单元测试可以 Mock 会话能力，Sa-Token 与 Redis 的真实行为由集成测试验证。
- 登录时，用户不存在和密码错误返回同一个 `AUTH_INVALID_CREDENTIALS`，避免通过响应差异枚举有效用户名。
- `LoginResponse` 只返回 Token、Token 名称、过期时间和安全的 `UserSummary`；`passwordHash` 不会进入响应模型。
- `/me` 通过 `requireLoginId()` 检查会话并读取用户 ID；Token 有效但用户已不存在时，先注销会话，再返回 `AUTH_REQUIRED`。
- `logout()` 通过会话适配器完成注销；无 Token 或重复退出保持幂等，不把“没有有效会话”误报为服务器错误。
- `AuthSessionIntegrationTest` 使用真实 MySQL、Redis、BCrypt、Sa-Token 和 MockMvc，验证注册、登录、`/me`、退出以及退出后原 Token 失效。
- 阶段 1 鉴权完成时全量测试为 86 项；测试方法继续遵循 `// [测试意图] ...` 单行说明规范。

### 单元测试方法模板（CollectionServiceTest）

一组 Service 单元测试通常可以压缩成三种模板。`CollectionServiceTest` 正是这三种模板的组合。

#### 模板 A：成功路径

```java
when(dependency.query(any())).thenReturn(...);

Result result = service.execute(request);

assertThat(result.field()).isEqualTo(...);
verify(dependency).write(any(Entity.class));
```

阅读 `shouldCreateCollectionForCurrentUser` 时，按给定、执行、断言三段理解：

```text
Given：当前用户是 1，查询没有同名集合，插入时数据库回写 ID 20
When：调用 createCollection
Then：断言返回摘要、实体字段、固定时间和 Mapper 收到的参数
```

#### 模板 B：业务失败

```java
when(dependency.query(any())).thenReturn(...);

assertThatThrownBy(() -> service.execute(...))
        .isInstanceOfSatisfying(
                BusinessException.class,
                exception -> assertThat(exception.getErrorCode())
                        .isEqualTo(ErrorCode.XXX)
        );

verify(dependency, never()).write(any(Entity.class));
```

失败测试的重点不是“抛了异常”四个字，而是同时确认：

- 异常类型是业务异常
- 错误码符合契约
- 失败路径没有执行后续副作用

#### 模板 C：只验证副作用

```java
when(dependency.selectCount(any())).thenReturn(1L);

service.ensureDefaultInbox(1L);

verify(dependency, never()).insert(any(Entity.class));
```

适合验证幂等、禁止重复插入、禁止越权更新和禁止删除受保护资源。

#### Mockito 语法分工

- `mock(Type.class)`：创建协作对象的替身，不访问真实 MySQL、Redis 或外部服务。
- `when(...).thenReturn(...)`：预置依赖方法的返回值。
- `when(...).thenAnswer(...)`：根据真实入参动态返回值，适合模拟数据库回写主键。
- `verify(...)`：验证 Service 是否真的调用了协作对象。
- `verify(..., never())`：验证失败路径没有执行危险副作用。
- `any()`、`anyLong()`、`any(Entity.class)`：参数匹配器；遇到重载方法时必须用带类型版本消除歧义。
- `ArgumentCaptor`：截获传给 Mapper 的实体，断言 Service 组装出的真实字段。

#### AssertJ 与异常断言

- `assertThat(...)` 用于普通返回值断言。
- `assertThatThrownBy(...)` 用于异常路径断言。
- `isInstanceOfSatisfying(...)` 同时断言异常类型和异常内部状态。
- `exception -> ...` 是 lambda：把捕获到的异常命名为 `exception`，继续断言它的 `ErrorCode`。

#### Java 类型与命名

- `1L`、`30L`、`40L` 是 `long` 字面量，用来模拟数据库 ID；`1` 是 `int`，在泛型和 `Long` 参数场景下语义不够明确。
- `LinkCollection.class` 是类字面量，用于 `ArgumentCaptor.forClass`、`any(...)` 和 `mock(...)`。
- record 使用 `result.name()`、`result.isInbox()`；普通实体使用 `entity.getName()`、`entity.getIsInbox()`。

阅读任意 Service 测试时，固定按以下顺序：

```text
1. [测试意图]
2. when 预置了什么依赖行为
3. Service 方法怎样被调用
4. assertThat / assertThatThrownBy 断言了什么
5. verify 验证了什么副作用
```

### 集合领域模型（阶段 2.1）

- `collection.user_id` 是所有权根字段；所有查询、更新、删除都必须同时限定当前登录用户，否则会出现水平越权。
- `uk_collection_user_name (user_id, name)` 是业务唯一约束的最终防线；Service 的 `existsByNameExcept` 只负责返回友好错误，不能替代数据库唯一索引。改名时它传入当前 `collectionId` 排除自身，所以"只改大小写"不再被误判为冲突；`createCollection` 传入 `null` 表示不排除任何行。
- `LinkCollection` 类名避开 `java.util.Collection`；实体字段 `isInbox` 通过 `@TableField("is_inbox")` 显式映射布尔列。
- 默认 Inbox 在用户注册的同一个数据库事务中创建；如果 Inbox 创建失败，用户注册也应回滚，避免产生没有收藏容器的用户。
- 集合 CRUD 的测试分层：`CollectionServiceTest` 验证业务规则和所有权，`CollectionControllerTest` 验证 HTTP 契约，`LinkCollectionMapperTest` 验证真实 MySQL 映射和唯一约束，注册集成测试验证默认 Inbox。
- `TINYINT(1)` 的显示宽度在 MySQL 8 中已废弃，Flyway 会给出提示但不影响 `BOOLEAN` 映射。
- 构造型 helper（如 `newCollection`）只把实体拼出来，落库由调用方负责。测试里"构造了但忘了 insert"不会有任何编译错误，而 `selectCount` 会安静地返回 0——看起来像"查重没命中"，实际是表里根本没有行。
- 因此"验证排除自身"的测试必须先把主键断言成非空。少了这一步，`ne(列, null)` 会让它靠 `id <> NULL` 恒为 unknown 而假通过，测试名字写的是"排除自身"，验证的却是一条恒假条件。

### 标签领域模型（阶段 2.2）

- `tag.user_id` 是所有权根字段；列表、改名和删除都必须同时限定当前登录用户，否则会出现水平越权。
- `uk_tag_user_name (user_id, name)` 与 collection 同构：唯一性作用域是「用户 + 名称」，不同用户可以各自拥有一个同名标签。
- 标签名不做 Java 侧大小写归一：列使用 `utf8mb4_0900_ai_ci`，`'java'` 在数据库里就等于 `'Java'`，Service 的查重直接交给数据库比较；自己再加一层 `toLowerCase()` 等于制造出第二套规则，迟早和数据库分叉。
- 改名时的查重必须排除自身，所以 `existsByNameExcept` 接收 `excludeId`：`createTag` 传 `null`，`updateTag` 传当前 `tagId`。排除自身的意义是让「只改大小写」不再被 `String.equals` 的大小写敏感误判成名称冲突。
- `ne(列, null)` 是 MyBatis-Plus 的拼接陷阱：它照样生成 `id <> NULL`，该表达式在 SQL 三值逻辑里恒为 `unknown`，`selectCount` 于是永远返回 0，查重静默失效。排他条件必须先在 Java 侧判空，再决定是否拼入。
- 标签 CRUD 的测试分层与集合一致：`TagServiceTest` 验证业务规则和所有权，`TagControllerTest` 验证 HTTP 契约，`TagMapperTest` 验证真实 MySQL 的字段映射与用户范围唯一约束。
- Service 单测把 Mapper 换成了 Mockito 替身，`selectCount` 的返回值是预置的，SQL 条件根本不参与执行；因此「查重恒返回 0」这类缺陷只能由真实数据库的 Mapper 测试暴露，两层测试谁也不能替代谁。

### 链接领域模型与所有权隔离（阶段 2.3）

- `link.user_id` 与 `link.collection_id` 是两条所有权链：前者决定"这条链接归谁"，后者决定"它被放在哪个集合"。写入前两条都要确认，缺一条就能把链接塞进别人的集合。
- 归属校验用 `id + user_id` 的联合条件，而不是"按 id 查出来再比 user_id"：一条 SQL 同时回答"存在吗"和"是我的吗"，也少了两次查询之间的竞态窗口。
- 别人的链接一律返回 `404` 而不是 `403`，让"不存在"和"不是你的"在响应上完全一致，避免通过状态码差异枚举出哪些 id 真实存在。
- 客户端只能传"要存什么"，不能传"这是谁的"：`user_id` 从会话推导，不进任何 DTO。这是最便宜的一道防越权设计。
- `UpdateLinkRequest` 刻意不含 `url` 字段：地址是链接的身份，改了地址就该是一条新链接。M4 之后每条链接会绑定自己的快照资产，允许改地址会让资产和地址对不上。
- 原样 URL 不适合直接做唯一键：`utf8mb4_0900_ai_ci` 不区分大小写，会把 `/Article` 和 `/article` 判成同一个地址，而很多站点的路径是大小写敏感的。设计上用 `CHAR(64) ascii_bin` 的哈希列做去重，比较语义就不再受排序规则影响。
- 唯一索引的落地位置要和"能算出索引列"的算法在同一个里程碑：`normalized_url`、`url_hash`、`uk_link_user_url` 三者全部依赖 URL 规范化，所以它们一起排在 M2.5，`V4` 只建 `original_url`。先建列再补算法，等于让表引用一个还不存在的概念。
- 数据库的 `ON DELETE CASCADE` 和外键是"允许删"的兜底，应用层的"非空拒删"才是"拦住删"的规则。两层各记一笔，将来改掉其中一层时另一边仍然有效。
- 集合"非空拒删"的判断必须排在 Inbox 保护之后。顺序颠倒时，非空 Inbox 会报成"集合非空"，用户按提示清空链接后第二次请求才会撞上真正的规则——错误信息等于误导。
- 链接计数用 `COUNT(*)` 而不是把数量冗余进集合表，换来的是永不漂移；代价是列表接口出现 N+1。这个取舍在集合数量还是个数级时成立，等 M6.2 做分页时再评估分组查询或冗余列。

### MyBatis-Plus 条件构造器的惰性求值（阶段 2.3）

- `LambdaQueryWrapper.eq(列, 值)` 不会立刻把值写进参数表：它把值包成惰性的 `ISqlSegment`，只有真正拼装 SQL 片段时才求值。所以构造完对象后立刻读 `getParamNameValuePairs()`，得到的永远是空 map。
- 想手动触发求值要调 `getSqlSegment()`，但这一步又需要先把 `Link::getUserId` 解析成列名，而解析依赖 `TableInfo`——它由 MyBatis-Plus 在启动扫描 Mapper 时注册。纯 Mockito 单元测试里没有这一步，调用会直接抛 `MybatisPlusException: can not find lambda cache for this entity`。
- 结论：**不要在单元测试里内省条件构造器。** Mock 会连条件对象一起吞掉，所以"Service 有没有记得拼 `user_id`"这类问题在 Mock 层证明不了；而测试自己 `new` 出来的 wrapper 又只证明了"框架的 `eq` 能用"，没证明"Service 记得拼"。这类断言的唯一可靠落点是集成测试——从 HTTP 入口一路打到真实 MySQL。
- 同一件事还有第二层：`ne(列, null)` 会拼出 `id <> NULL` 而恒为 unknown（见 2026-10-13 排错笔记）。两条合起来说明同一个道理——**依赖 SQL 语义的正确性，只能在真实数据库上证明。**

### 标签关联与联合主键（阶段 2.4）

- `link_tag` 是纯关联表，主键是 `(link_id, tag_id)`。列顺序按最高频查询的最左前缀来定：`(link_id, tag_id)` 让"查某条链接挂了哪些标签"走主键；颠倒成 `(tag_id, link_id)` 会让这个最热的操作退化成扫描。
- 联合主键表在 MyBatis-Plus 里要声明一个逻辑主键，否则启动会打 `Can not find table primary key` 的 WARN。代价随之而来：`deleteById(任何 id)` 都会按 `link_id` 匹配，所以这张表所有条件一律走 `LambdaQueryWrapper`，禁用 `selectById` / `deleteById` / `updateById`。
- `tag_id` 上不用手写 `KEY`：InnoDB 会为外键列自动建索引，而联合主键最左列是 `link_id`，`tag_id` 用不上它。InnoDB 拒绝创建外键除非存在可用索引，所以这个索引是由约束保证存在的，不是碰运气。
- 两个外键都写 `ON DELETE CASCADE`，但业务语义正好相反：删链接要连带清掉关联，删标签只清关联、链接必须活着。同一个写法在一处是兜底、在另一处是正主，所以 `TagService.deleteTag` 一行显式删除都不需要。
- 校验标签归属用一次 `IN` + `COUNT`：查到的条数等于请求的条数，就说明这批 id 全部归我。空集合直接放行，省掉一次无意义的往返。
- 标签 id 必须在写入前去重，否则 `[1, 1]` 会撞上联合主键。去重放在服务层而不是 DTO 的紧凑构造器里，因为 `CreateLinkRequest` 与 `SetLinkTagsRequest` 要共用同一套规则。
- 容器元素约束 `List<@NotNull Long>` 能拦住 `[1, null]`：`@NotNull` 写在尖括号里的 `Long` 前面，校验的是集合里的每个元素；写在 `List` 前面校验的只是列表本身。实测 `[1, null]` 在控制器边界就判 `400`，没有走到数据库的 `NOT NULL` 列。
- `link_tag` 不带 `user_id`，因为 `tag_id` 已经唯一确定一个用户；前提是关联写入时强制"链接与标签同属一人"。省略一个字段必须由一条写在代码里的不变量支撑，否则保护一放开就会静默算错。
- `TagSummary.linkCount` 从写死 `0L` 换成真实计数后，`listTags` 出现已知的 N+1。取值策略与集合侧对称：新建传字面量 `0L`，改名与列表查真实值。

### 文档同步规则

- 测试数量、接口“已实现/未实现”和鉴权方案必须以当前代码与可重复执行的测试为准，不能沿用早期规划文案。
- 阶段性验收数字保留原值并标明“验收时”，新增“当前状态”记录最新结果；这样既不篡改历史，也能让索引反映现实。
- 文档中提到的技术如果是“计划采用”，要明确写成计划；例如 JWT 只作为后续对照实验，不是当前鉴权依赖。
