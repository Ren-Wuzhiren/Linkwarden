# 2026-09-17 阶段 1.2B2.1 复盘

## 本轮目标

在阶段 1.2B1 完成统一成功响应后，建立统一错误响应协议，为后续业务异常、参数校验和健康检查提供稳定的数据结构。

本轮只实现错误数据模型，不实现 `GlobalExceptionHandler`、健康检查和 MyBatis-Plus 配置。

## 已完成

- 新增 `docs/需求文档/2026-09-17-004-阶段1.2B2-统一错误与健康检查.md`，明确错误码、HTTP 状态、details 和健康检查语义。
- `ErrorCode` 改为枚举，每个错误码绑定 HTTP 状态和默认中文消息。
- `ErrorResponse` 使用私有构造器和工厂方法创建，包含 `code`、`message`、`details`、`requestId`。
- `details` 为 `null` 时规范化为 `{}`，非空时使用 `Map.copyOf` 保存不可变快照。
- `requestId` 在创建错误响应时从 `RequestIdContext` 取得，不允许调用方伪造。
- 新增 `ErrorCodeTest` 2 个、`ErrorResponseTest` 5 个测试。

## 暴露的问题

- `ErrorCode` 最初被写成普通类，并混用了实例字段和静态整数常量，无法表达每个错误码对应的状态与默认消息。
- 几个 HTTP 状态码最初写错，`CONFLICT`、`INTERNAL_ERROR` 和 `SERVICE_UNAVAILABLE` 被误写成 400。
- `ErrorResponse` 工厂方法最初只有方法签名，没有返回值，导致 Maven 编译失败。
- 构造器最初是公开的，允许调用方绕过工厂设置任意 requestId。
- details 最初直接引用调用方传入的 Map，并且没有处理 null，破坏了响应协议和快照边界。

这些问题说明：编译成功、方法存在和设计正确不是同一件事；需要从调用者视角补测试。
