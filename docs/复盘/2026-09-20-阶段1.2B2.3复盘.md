# 2026-09-20 阶段 1.2B2.3 复盘

## 本轮目标

在前两轮完成统一错误协议和全局异常转换后，建立进程存活、依赖就绪和 MyBatis-Plus 分页配置，使应用可以在真实 MySQL、Redis 环境下启动并接受健康检查。

本轮不实现用户表、鉴权拦截器和业务资源。

## 已完成

- `GET /api/v1/health/live` 返回进程存活的 `ApiResponse`，不访问外部依赖。
- `GET /api/v1/health/ready` 检查 MySQL 连接有效性和 Redis `PING/PONG`。
- MySQL 或 Redis 不可用时抛出 `BusinessException`，由全局异常处理器返回 HTTP 503 和 `SERVICE_UNAVAILABLE`。
- 检查某一个依赖失败时仍继续检查另一个依赖，details 同时返回 `mysql`、`redis` 状态。
- `MybatisPlusConfig` 注册 `PaginationInnerInterceptor(DbType.MYSQL)`。
- 新增 `HealthControllerTest`、`HealthCheckServiceTest`、`MybatisPlusConfigTest`。

## 验证结果

```text

BUILD SUCCESS
```

真实环境手工验证：

- Docker Compose 中 MySQL 8.4 与 Redis 7.4 均达到 `healthy`；
- Spring Boot 在 `8082` 临时启动成功；
- `live` 返回 `data.status=UP`；
- `ready` 返回 `data.mysql=UP`、`data.redis=UP`；
- 错误配置 Redis 密码时，`ready` 返回 HTTP 503 且 details 为 `redis=DOWN`、`mysql=UP`。

## 暴露的问题

- MySQL 和 Redis 容器停止后，Flyway 按 fail-fast 规则终止应用，日志表现为 `Connection refused`。
- 用户级 `SPRING_DATA_REDIS_PASSWORD` 覆盖了 `application-local.yml` 中的密码，导致 Redis `WRONGPASS`；这说明 Spring Boot 环境变量优先级必须纳入排错范围。
- 重复启动应用时 `8080` 被旧实例占用，错误发生在 Tomcat 启动阶段，而不是 Controller 或业务代码。
- 仅查看 `Connection refused` 无法判断故障组件，必须结合 `Caused by` 和调用栈区分 JDBC、Lettuce 或 HTTP 客户端。

## 学习收获

- `live` 和 `ready` 解决的是不同问题：前者描述进程，后者描述依赖和业务准备状态。
- 健康检查不是简单调用端口，MySQL 要验证连接有效性，Redis 要验证认证和命令执行。
- try-with-resources 是连接池资源安全的基础；只获取连接不关闭会造成资源泄漏。
- 环境变量、配置文件、命令行参数存在明确优先级，修改 YAML 不一定能覆盖运行环境。
- 排错时必须结合端口、容器、进程、环境变量和调用栈，而不是根据单个关键词下结论。
