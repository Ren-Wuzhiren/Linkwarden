# 2026-09-20 阶段 1.3 复盘

## 本轮目标

建立系统第一张业务表 `app_user`，用 Flyway 管理建表脚本，并验证用户身份主表在真实 MySQL 中可以安全落地。

本阶段只做数据库迁移，不实现 Java 实体、Mapper、注册和登录。

## 已完成

- 创建 `V1__create_app_user.sql`。
- 建立 `app_user` 表：
  - `id`：自增主键；
  - `username`：非空、唯一、最长 32 字符；
  - `email`：可空、唯一、最长 254 字符；
  - `password_hash`：保存 BCrypt 等密码哈希，最长 100 字符；
  - `created_at`、`updated_at`：毫秒精度，由业务代码按 UTC 语义写入。
- 使用 `InnoDB`、`utf8mb4` 和 `utf8mb4_0900_ai_ci`。
- Flyway 成功执行迁移并记录版本、描述、校验和与成功状态。
- 通过事务验证用户名唯一、邮箱唯一和多个 `NULL` 邮箱共存，验证后回滚。

## 暴露的问题

- 首次使用 `V1_create_app_user.sql` 时，Flyway 检测到了文件但不执行，因为版本号后必须有双下划线。
- 初始 SQL 在迁移文件中执行 `CREATE DATABASE` 和 `USE`，而 Flyway 已经连接到 `application-local.yml` 指定的数据库；数据库创建不属于当前迁移职责。
- 初始字段名写成 `create_at`、`update_at`，与 Java 实体映射约定 `created_at`、`updated_at` 不一致。
- MySQL 客户端在当前终端显示中文表注释为问号，但十六进制检查证明 UTF-8 数据实际正确。

## 学习收获

- Flyway 文件名不是普通命名：`V<version>__<description>.sql` 的版本分隔符是两个下划线。
- Flyway 迁移只负责当前配置数据库内的 schema 演进，首次执行后不得修改已执行文件。
- 唯一约束是数据库层最后防线；业务层提前检查不能替代数据库约束，因为并发请求仍可能同时通过检查。
- MySQL 唯一索引允许多个 `NULL`，因此可选邮箱可以留空，但业务层必须把空字符串规范化为 `NULL`。
- 看到终端乱码不能直接判断数据库损坏，应通过字节编码、`HEX()` 或 UTF-8 客户端进一步验证。
