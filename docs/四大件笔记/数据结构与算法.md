## 阶段 1.2：标识与关联

已观察到的真实实现：

- `requestId` 用 UUID 作为缺失或非法请求头时的替代标识。
- UUID 的设计目标是实际使用中极低碰撞概率，不等于数学意义上的绝对唯一，也不能作为安全凭证。
- `ThreadLocal` 把同一个请求 ID 与当前处理线程关联起来，但本阶段没有研究 `ThreadLocalMap` 的底层结构。

## 阶段 1.4：规范化、唯一性与索引

已通过代码和数据库验证：

- 用户名和邮箱在进入校验与持久化前先规范化：`strip()` 处理首尾空白，邮箱固定用 `Locale.ROOT` 小写化，空白邮箱转成 `null`。
- 规范化必须发生在校验之前，否则“输入时长度为 6、规范化后长度为 2”的字符串会绕过长度规则；这体现了数据表示顺序会影响算法正确性。
- `app_user.username` 和 `app_user.email` 的 `UNIQUE KEY` 由数据库索引承担并发下的唯一性最终保障，业务层的先查询再插入不能替代它。
- `email = NULL` 允许重复，是因为 SQL 唯一索引对 `NULL` 的语义与普通值不同；这属于数据模型约束，不是简单的集合去重。
