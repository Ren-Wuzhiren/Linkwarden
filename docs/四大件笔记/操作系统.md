## 阶段 1.2：线程、线程池与资源限制

已通过代码和测试验证：

- Servlet 容器使用线程处理请求，线程会被复用，因此 `RequestIdContext` 的 `ThreadLocal` 数据必须在 `finally` 中清理。
- 测试证明请求完成后 `RequestIdContext.get()` 和 MDC 中的值都会恢复为 `null`，避免下一个请求继承旧编号。
- HikariCP 通过 `maximum-pool-size=10`、`minimum-idle=2` 和 `connection-timeout=3000` 限制和复用数据库连接。
- MySQL 和 Redis 通过 Docker 容器运行，容器是资源隔离边界；Compose 停止容器不会删除命名数据卷。
- Windows 的 Docker API 通过命名管道暴露；引擎未启动时，客户端看到的是管道不存在，而不是项目路径错误。

当前边界：

- 尚未实现异步任务和 Worker 并发，不能提前声称掌握了任务锁和故障恢复。
- 还需要在后续阶段观察文件描述符、磁盘 I/O 和容器资源上限。

## 阶段 1.4：外部会话与测试容器

已通过代码和测试验证：

- Sa-Token 的会话状态放到 Redis，认证不只是 JVM 内的一次密码比较；会话的创建、读取和删除都跨越应用进程与外部存储边界。
- `SaTokenRedisIntegrationTest` 验证写入、读取、TTL 和删除，说明“过期自动失效”和“主动退出删除”是两条不同的生命周期。
- Testcontainers 为测试启动独立的 MySQL 和 Redis 容器，Ryuk 在 JVM 退出时回收测试容器；测试环境的资源和正式 Compose 环境隔离。
- 应用重启后的登录状态取决于 Redis 数据是否仍在，不能把 JVM 内存当成可靠会话存储。

当前边界：

- 还没有实现 Worker 并发、任务锁和失败恢复；Redis 当前作为鉴权会话存储的事实，不能替代对任务队列并发的学习。

## M2.1–M2.4：事务边界、检查再插入与资源占用

| 里程碑 | 本节取用的真实产物 |
| --- | --- |
| `M2.2` | 标签唯一约束与“先查重再插入”的调用链 |
| `M2.3` | `createLink` 的事务边界、集合非空拒删 |
| `M2.4` | `PUT /links/{id}/tags` 的先删后插、两条级联外键 |

已通过代码和测试验证：

- `PUT /links/{id}/tags` 的“先删掉这条链接的全部关联、再逐条写入新关联”在同一个事务里完成，外部读不到“标签全空”的中间态。
- `createLink` 在同一个事务里先插链接、再写关联：要么两者一起成功，要么一起回滚，不会留下“链接存了但标签丢了”的半截状态。
- 依赖外键级联的清理都不写成业务代码：`link_tag` 的两条外键都是 `ON DELETE CASCADE`，删链接或删标签时由数据库完成级联。
- “先查重再插入”是检查与使用之间存在时间窗，并发下不能单独依赖它，最终保障仍然是数据库唯一键。
- 顺序本身也是设计：先确认链接归我、再确认标签全部归我，两道校验都通过之后才动数据，避免“已经删掉旧关联，才发现新标签不合法”。
- N+1 把一次请求内的查询次数从 O(1) 放大到 O(n)，连接被占用的时间同比拉长。

```text
PUT /links/{id}/tags 的先删后插在同一事务内        → LinkService.setLinkTags
createLink 先插链接、再写关联                     → LinkService.createLink
两条外键 ON DELETE CASCADE                        → V5__create_link_tag.sql
先查重再插入留有时间窗                            → TagService.existsByNameExcept
N+1 放大单次请求的查询次数与连接占用              → TagService.listTags、CollectionService.listCollections
```

当前边界：

- 还没有实现异步任务与 Worker 并发；本阶段观察到的只是单请求内的事务边界，不能替代对任务锁与故障恢复的学习。
- 连接池的上限已在阶段 1.2 验证过，但“一次请求占用连接多久”没有测量；N+1 的代价目前只是次数推算。
