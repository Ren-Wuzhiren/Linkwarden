## 待项目验证

- 文件描述符、磁盘 I/O、进程隔离与容器限制。
- 锁、超时和故障恢复。

## 阶段 1.2：线程、线程池与资源限制

已通过代码和测试验证：

- Servlet 容器使用线程处理请求，线程会被复用，因此 `RequestIdContext` 的 `ThreadLocal` 数据必须在 `finally` 中清理。
- 测试证明请求完成后 `RequestIdContext.get()` 和 MDC 中的值都会恢复为 `null`，避免下一个请求继承旧编号。
- HikariCP 通过 `maximum-pool-size=10`、`minimum-idle=2` 和 `connection-timeout=3000` 限制和复用数据库连接。
- MySQL 和 Redis 通过 Docker 容器运行，容器是资源隔离边界；Compose 停止容器不会删除命名数据卷。
- Windows 的 Docker API 通过命名管道暴露；引擎未启动时，客户端看到的是管道不存在，而不是项目路径错误。

当前边界：

- 尚未实现异步任务和 Worker 并发，不能提前声称掌握了任务锁和故障恢复。
- 还需要在后续阶段观察文件描述符、磁盘 I/O 和容器资源上限。

## 阶段 1.4：外部会话与测试容器

已通过代码和测试验证：

- Sa-Token 的会话状态放到 Redis，认证不只是 JVM 内的一次密码比较；会话的创建、读取和删除都跨越应用进程与外部存储边界。
- `SaTokenRedisIntegrationTest` 验证写入、读取、TTL 和删除，说明“过期自动失效”和“主动退出删除”是两条不同的生命周期。
- Testcontainers 为测试启动独立的 MySQL 和 Redis 容器，Ryuk 在 JVM 退出时回收测试容器；测试环境的资源和正式 Compose 环境隔离。
- 应用重启后的登录状态取决于 Redis 数据是否仍在，不能把 JVM 内存当成可靠会话存储。

当前边界：

- 还没有实现 Worker 并发、任务锁和失败恢复；Redis 当前作为鉴权会话存储的事实，不能替代对任务队列并发的学习。
