# Linkwarden v2.16.3 设计取舍与可迁移结论

## 值得迁移的设计

- 保存操作与保存执行分离：HTTP 请求只创建业务记录，耗时的浏览器操作交给 Worker。
- 数据库是事实来源，搜索索引是可重建的派生数据。
- 多格式保存彼此隔离：某一种格式失败不应让整条链接丢失。
- URL 安全检查必须在普通 HTTP 抓取、重定向和浏览器子请求三个层面执行。
- 文件访问抽象成统一接口，先用本地文件系统，未来可以替换 S3/MinIO。
- 浏览器按批复用，既能摊薄启动成本，也需要空闲回收和超时轮换。
- 搜索先取 ID，再回数据库补全并复核权限，避免索引泄漏。

## 不应照搬的部分

- 不迁移订阅、计费、多人协作、公开分享、RSS、SSO 和移动端。
- 不把截图、PDF、HTML 路径全部塞进一张业务表。
- 不用 `lastPreserved = null` 同时表达待处理、执行中和失败。
- 不依赖无限循环轮询而不记录任务租约和重试次数。
- 不把浏览器、Monolith 和全部保存格式都放进第一版必须完成的范围。

## Java/Vue 版本的设计结论

- 使用模块化单体，`api` 和 `worker` 是同一后端的两个 profile。
- `capture_job` 是可靠任务源，使用 MySQL `FOR UPDATE SKIP LOCKED` 抢占，Redis 只做锁、限流和缓存。
- `asset` 独立记录文件路径、类型、大小、哈希和采集批次。
- 第一版支持截图、PDF 和 HTML；Readability 正文抽取作为内嵌能力，不单独暴露外部依赖。
- 搜索先使用 MySQL ngram 全文索引；需要更强相关性和分页时再评估 Meilisearch。
- 先实现真正的端到端闭环，再增加重新采集、失败重试和更多格式。

## 面试可讲的问题

- 为什么保存任务不能直接在 Web 请求线程中执行？
- 如何阻止 SSRF，为什么重定向后还要再次校验？
- 为什么数据库状态和搜索索引会不一致，如何补偿？
- `FOR UPDATE SKIP LOCKED` 如何避免多个 Worker 抢占同一任务？
- 如何处理浏览器崩溃、任务超时和部分格式失败？
- 为什么第一版不上 MinIO/Meilisearch，什么时候才值得升级？
