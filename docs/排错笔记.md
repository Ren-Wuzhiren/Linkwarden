# 排错笔记

> 记录真实故障、现象、定位过程、根因和修复结论。只记录实际发生的问题。

## 2026-09-12 Docker 拉取 Meilisearch 返回 502

- 现象：首次 `docker compose up` 时，`dockerproxy.net` 返回 502，PostgreSQL 镜像拉取也被中断。
- 定位：Docker `RegistryConfig.Mirrors` 配置为 `https://dockerproxy.net/`。
- 处理：不立即修改全局 Docker 配置，先执行 `docker compose pull` 重试；第二次拉取成功。
- 结论：镜像加速器的 502 可能瞬时出现，先重试并确认是单次故障，再考虑调整全局配置。

## 2026-09-12 PostgreSQL 无法绑定 5433

- 现象：Docker 端口映射到宿主 `5433` 时报 `bind: An attempt was made to access a socket in a way forbidden by its access permissions`。
- 定位：`netsh interface ipv4 show excludedportrange protocol=tcp` 显示 `5360-5459` 在 Windows 排除区间内。
- 处理：把 PostgreSQL 宿主端口改为 `55432`，同时更新本地 `.env` 的 `DATABASE_URL`。
- 结论：Windows 上 Docker 端口冲突不一定是进程占用，也可能是系统保留区间。

## 2026-09-12 Yarn 4 安装出现 EXDEV

- 现象：Yarn 下载依赖后，把缓存临时文件重命名为正式文件时反复出现 `EXDEV: cross-device link not permitted`。
- 定位：当前目录可见路径都在 C 盘，但用户 AppData 目录带加密/重解析环境；Corepack 包装进程仍使用默认全局缓存。
- 处理：使用 Node 20 直接调用 `reference/tools/corepack/v1/yarn/4.12.0/yarn.js`，并设置 `YARN_CACHE_FOLDER` 到 D 盘、`YARN_ENABLE_GLOBAL_CACHE=false`。
- 结果：依赖安装完成，Prisma Client 生成，patch-package 和 Playwright Chromium 安装成功。

## 2026-09-12 Next.js 启动出现 EXDEV

- 现象：Next.js 启动时写 `AppData\Roaming\nextjs-nodejs\Config\config.json` 失败，web 进程退出。
- 根因：Next.js telemetry 配置写入路径触发了同类跨卷重命名问题。
- 处理：设置 `NEXT_TELEMETRY_DISABLED=1` 后重启。
- 结果：Next.js 在 2.1 秒内 Ready，`http://localhost:3000` 返回 HTTP 200，worker 四个循环正常启动。

## 2026-09-14 Docker 提示找不到 dockerDesktopLinuxEngine

- 现象：执行 `docker compose -f deploy/local/docker-compose.yml up -d` 时提示 `npipe:////./pipe/dockerDesktopLinuxEngine` 不存在。
- 定位：Docker CLI 正常，但 Docker Desktop 进程没有运行，WSL 中的 `docker-desktop` 发行版处于 `Stopped`，因此 Compose 路径和 YAML 都没有问题。
- 处理：通过可见窗口启动 Docker Desktop，等待 `docker info` 可以读取 Server 版本后重新执行 Compose。
- 结论：先验证 `docker info`，再验证 Compose；不要把 daemon 未启动误判为 Compose 文件路径错误。

## 2026-09-14 Docker Hub 直连拉取镜像超时

- 现象：引擎启动后，`mysql:8.4` 和 `redis:7.4-alpine` 拉取时连接 `registry-1.docker.io:443` 超时。
- 定位：Docker 当前没有配置 registry mirror，本地已有版本匹配的缓存镜像。
- 处理：确认缓存镜像分别是 MySQL 8.4.11 和 Redis 7.4.11，并给它们补齐 `mysql:8.4`、`redis:7.4-alpine` 本地标签后启动。
- 结果：MySQL 与 Redis 容器均达到 `healthy`；Compose 文件仍使用标准镜像名，不绑定当前机器的特殊标签。

## 2026-09-15 Spring 环境变量覆盖本地 Redis 密码

- 现象：应用启动成功，但 Actuator 健康状态为 `DOWN`，异常链显示 Redis `WRONGPASS invalid username-password pair or user is disabled`。
- 定位：容器实际使用 `webcollector_dev` 可以通过 `PING`；用户级环境变量 `SPRING_DATA_REDIS_PASSWORD` 存在，且 Spring Boot 环境变量优先级高于 `application-local.yml`。
- 处理：只在实际运行进程中移除该环境变量后重新启动，项目配置和用户级环境变量均保持不变；健康状态恢复为 `UP`。
- 结论：排查连接认证问题时要同时检查配置文件、Compose 环境和 Spring 环境变量，不能只看 YAML。

## 2026-09-15 测试类放错源码目录导致 JUnit 找不到

- 现象：`RequestIdContextTest.java` 放在 `src/main/java`，执行 Maven 时在 `compile` 阶段报找不到 `org.junit.jupiter.api`。
- 定位：`spring-boot-starter-test` 是 `test` 作用域，只在测试编译 classpath 中可见；`src/main/java` 属于主代码编译范围。
- 处理：把测试类移动到 `src/test/java/com/webcollector/common/web/`。
- 结论：不要通过把测试依赖改成 `compile` 来绕过问题，应该修正源码目录边界。

## 2026-09-15 RequestIdFilter 编译失败

- 现象：`MDC.put(MDC_KEY, );` 导致 Java 在主代码编译阶段报“非法表达式开始”，测试没有运行。
- 定位：MDC 调用缺少第二个参数；同时存在无关 Swagger `Header` 导入、空的 `resolveRequestId` 和无意义吞异常的 `catch`。
- 处理：补齐 `requestId` 参数，删除无关导入和吞异常逻辑，实现 UUID 兜底，并在 `finally` 清理 MDC 与 ThreadLocal。
- 结果：主代码可以编译，Filter 的 4 个测试与 Context 的 2 个测试全部通过。

## 2026-09-20 Compose 未运行导致 Flyway 连接拒绝

- 现象：Spring Boot 启动片刻后自动结束，日志出现 `java.net.ConnectException: Connection refused`；客户端访问 `localhost:8080` 也得到同类异常。
- 定位：Docker Engine 正常，但 `docker compose ps` 没有任何容器；`3307`、`6380`、`8080` 均没有监听者。Flyway 无法连接 `localhost:3307`，应用按 fail-fast 规则取消启动。
- 处理：执行 `docker compose -f deploy/local/docker-compose.yml up -d`，等待 MySQL 和 Redis 进入 `healthy` 后再启动 Spring Boot。
- 结论：`Connection refused` 只说明目标地址和端口没有监听者，必须查看异常栈判断是 MySQL、Redis 还是 HTTP 应用；不能仅凭这一行判断具体组件。

## 2026-09-20 重复启动导致 8080 被占用

- 现象：第二次启动 Spring Boot 时提示 `Web server failed to start. Port 8080 was already in use`。
- 定位：`8080` 已由前一个 `com.webcollector.WebCollectorApplication` Java 进程监听；重复启动产生了第二个 Tomcat 实例。
- 处理：保留已有实例并直接测试，或先在 IDEA/终端停止旧实例，再启动新实例。排查端口时使用 `Get-NetTCPConnection`、`netstat -ano` 和 `Get-CimInstance Win32_Process` 关联 PID、命令行和父进程。
- 结论：`Get-NetTCPConnection` 找不到对象通常表示端口空闲，不是端口被隐藏；只有 `netstat` 和进程关联查询都有结果时，才需要判断是否结束进程。

## 2026-09-20 Flyway 检测到文件但未执行迁移

- 现象：Spring Boot 启动日志显示 `1 SQL migrations were detected but not run because they did not follow the filename convention`，随后显示 `Successfully validated 0 migrations`。
- 定位：迁移文件名为 `V1_create_app_user.sql`，版本号与描述之间只有一个下划线；Flyway 默认约定要求 `V1__create_app_user.sql`。
- 处理：按 `V<version>__<description>.sql` 重命名文件，移除迁移中的 `CREATE DATABASE`、`USE`、`SELECT DATABASE()` 和 `SHOW TABLES`，让迁移只操作 Spring 配置已经选定的数据库。
- 结果：Flyway 执行版本 `1`，`flyway_schema_history` 记录 `success=1`。
- 结论：迁移文件被检测到不代表会被执行；文件名、版本号和数据库边界都要同时符合 Flyway 约定。

## 2026-09-20 MySQL 表注释显示问号

- 现象：在 Docker MySQL 客户端执行 `SHOW CREATE TABLE app_user` 时，表注释显示为 `COMMENT='?????'`。
- 定位：查询 `information_schema.TABLES.TABLE_COMMENT` 并转换为十六进制，得到 `E794A8E688B7E8B4A6E58FB7E8A1A8`，与“用户账号表”的 UTF-8 字节一致。
- 处理：不修改数据库内容，确认这是当前 PowerShell/MySQL 客户端输出编码问题。
- 结论：终端乱码只能证明“显示和编码链路存在问题”，不能直接证明数据库存储损坏；应使用 `HEX()` 或 UTF-8 客户端复核。
